이 문서와 `delivery.json` 이 "어느 25줄이 전달본인가"에 대한 **유일한 기준**이다.
`docs/02_RESEARCH.md`, `docs/03_RESEARCH_459.md` 는 작성 시점의 연구 기록이며
그 안의 "확정" 표현은 이 문서보다 앞선다.

## 1. 지금 해야 할 일

`delivery.json` 의 `"purchased"` 가 `null` 이다. **실제로 구매한 세트 이름을 적어라.**

```json
"purchased": "U25_L1_POP35"        // 또는 "U25_L1_FILT_MAXCOV"
```

적기 전에는 `code/score.py` 가 채점을 거부한다(종료코드 2). 의도된 동작이다.
당첨번호를 본 뒤에 성적 좋은 쪽을 전달본이라고 부르면 실적 기록이 무의미해진다.

구매하지 않았다면 `"purchased": "none"` 이라고 적고 그 회차는 실적표에서 뺀다.

### 몫배수 — 직접 비교하지 말 것

| 세트 | (a) n_le12 단일특징 | (b) 번호별 감마 (현행) |
|---|---|---|
| `U25_L1_POP35` | ×1.0328 | **×1.0501** |
| `U25_L1_FILT_MAXCOV` | **×1.0399** | ×1.0253 |

**각 세트는 자신이 최적화된 모형에서 더 높게 나온다.** 이건 성능이 아니라 순환이다.
두 모형 중 어느 쪽을 믿을지는 이 25줄이 아니라 보류구간 전향 검증으로 정한다.
번호별 감마 모형은 1144~1243회(학습에 쓰지 않은 100회)에서
r=+0.852, t=+16.13, p=2.5e-29 로 재현됐다. 그래서 (b) 기준을 채택하고
`U25_L1_POP35` 를 권장한다. 근거는 그것뿐이며, 어느 쪽도 당첨 확률은 같다.

### 기록된 수치의 불일치 — 보고

`results/FINAL_1244.json` 의 `mult: 1.03993` 은 **n_le12 단일특징 모형**
(`w = exp(-0.0694 × n_le12)`, 스크립트 `final_run.py`)의 산출값이다.
`results/FINAL_POP35.json` 의 `mult: 1.05006` 은 **번호별 감마 모형**
(`lotto_core.share_multiplier`)의 산출값이다.

두 파일의 `mult` 필드는 같은 척도가 아니다. 원본 파일은 보존하되
**두 파일의 `mult` 를 나란히 놓고 비교하지 말 것.** 같은 척도의 값은 위 2×2 표와
`delivery.json` 의 `properties` 에만 있다.

## 4. 추첨 후 절차

```bash
# 1) delivery.json 의 purchased 를 먼저 채운다
cd code
python score.py --winning 3 9 14 22 30 41 --bonus 7          # 실제 당첨번호로
python score.py --winning ... --bonus 7 --all                 # 참고 세트도 함께
```

2. `docs/HANDOFF.md` 9절 실적표에 **구매한 세트만** 한 줄 추가한다.
3. 등수별 당첨게임 수를 받으면 `data/tier_winners_784_1243.csv` 에 이어 붙인다.
4. 20회 이상 쌓이면 `python verify_gamma.py` → `python estimate_popularity.py` 로 감마를 갱신한다.
5. `python generate.py --round 1245` 로 다음 회차를 만들고 새 `delivery.json` 을 쓴다.

결과를 보고 시드·컷·제약을 바꾸지 않는다.
